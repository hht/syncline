# Syncline architecture decisions

Records architecture decisions made by the team: what was chosen, what was rejected, and why. Implemented rules follow the code, tests, and models ([Models and model checking](model.md)), which serve as the source of truth and are not duplicated here.
Every decision can be reconsidered: if a better approach is found, present a comparison table for decision, and update this document once settled.

- Column-level last-write-wins on the cloud, following Drizzle foreign keys with cascade deletes, rejecting writes that reference deleted parent rows, without writing per-table mutators. Trade-off: when two devices concurrently read and modify the same column, the later write overwrites the earlier one.
- Point-in-time recovery without sealing: devices whose cookie is not on the restored history perform a full refetch, and pending writes push normally; mutation identities `(client, id)` are immutable, and gaps in mutation IDs are jumped by the cloud (renumbering mutations would cause a device restored from an old backup to execute the same mutation twice). Trade-off: recovery cannot undo writes that devices have not yet pushed.
- Commit log records only touched keys; pulls read current values, capped by bytes (at most 0.25× data size, at least 64 MB), with oldest commits truncated by upkeep chores when exceeded; devices with a cookie earlier than the log floor perform a full refetch (shared spaces return `reset`). Rejected: time-based retention (unbounded under heavy write loads) and value-bearing commit logs (~5.7× storage in private spaces). Trade-off: devices offline for a long period must perform a full resync; once the log reaches its cap, each commit writes 1 extra row.
- Exactly one encoding for primary keys and positions: primary keys are encoded into text with columns ordered by column name; positions universally use the reader encoding (the checksum start is its scan point, and exports persist reader positions). Dual encodings rejected: before production launch, internal tables were collapsed to a single version, staging was wiped, and device databases were dropped (decided 2026-10-29).
- Table and column names permit only ASCII letters, digits, and underscores, without starting with a digit: names are interpolated directly into SQL JSON paths and used as keys in primary-key objects without escaping. Trade-off: integrators cannot use other identifiers (decided 2026-10-29).
- Table names follow SQLite in ignoring ASCII case, refused at the declaration boundary: names differing only by case (synced, local-only, shared space, and retired names) are one name, and a table must be declared under the case it is stored as, on devices and in the cloud; retired names are resolved to the stored names where Syncline reads them (devices installed, and objects created, before and after a release changing only the case store different names yet share one retired list); Syncline itself then records and compares names exactly. Rejected: comparing case-insensitively throughout (`_syncline_declared` with `NOCASE` and every comparison folded: many scattered sites, each a place to miss). Trade-off: integrators cannot change only the case of a table name; they use a new name and retire the old one (decided 2026-11-04).
- Retired names are never declared again, by synced, local-only, or shared tables, and retiring drops only tables some space still records, so local-only writes are lost only to an owner switch, to a space declaring their table, or to the app dropping it: a table that left sync earlier (local-only since or not) keeps its rows until the private owner switches, like any table that left sync. Rejected: letting local-only tables reuse retired names (what a device then holds under the name depends on the releases it went through: one device drops the old table, another keeps it and cannot open under a new shape); dropping every retired table that was ever synced (loses local-only writes made after it left sync). Trade-off: a name once retired cannot be used again even locally, and a table retired after it left sync takes space until the next owner switch (decided 2026-11-04).
- Scope changes (tables or columns entering sync, or bucket rules changing in shared spaces) record only the version `since` which each change applies in the scope table; pulls first drop leaving tables, then scan entering tables, and finally chase incremental tail commits, following ElectricSQL where modifying a shape invalidates it and clients re-download only that shape. Rejected: backfilling entries on the write side (extra writes, a duplicate copy, potentially exceeding 10 GB). Trade-off: each lagging device re-downloads the table.
- A private space is a full replica on the device; the device must hold the entire space; no partial sync.
- Switching accounts with pending writes from the previous user: do not clear; opening fails with an error (`PendingWrites`, reporting the previous user and write count). The integrator can have the user log back in to finish syncing before switching, or explicitly pass `discardPending` when opening; background sync never discards. Rejected: clearing automatically (PowerSync `disconnectAndClear` wipes pending writes along with synced data, leaving the app to check `getUploadQueueStats` first), which permanently loses unuploaded writes. Rejected: one local database per user (leaves the previous user's data on the device). Trade-off: integrators must handle this error; unhandled, opening fails after switching accounts.
- Explicit resync (`resync`) preserves unuploaded writes by default: full pull from scratch, swapping synced tables on landing, and pending writes replay and push normally (sharing the code path with refetch after PITR, modeled as `Refetch`); pending writes are discarded only when `discardPending` is passed. When an individual mutation in a push has unrecognizable changes but a recognized identity, the cloud holds that mutation and advances the sequence number rather than rejecting the entire batch, so the device does not need to discard pending writes to unblock; only unrecognizable batches (invalid batch format, exceeding limits, or unrecognizable mutation identity) are rejected with status 1007, stopping further pushes, which fails `sync()` immediately until sync restarts or `resync()` runs (the batch is then pushed and rejected again); `resync({ discardPending: true })` drops pending writes to stop the rejections. Rejected: wiping on resync, which drops unpushed writes upon a single resync (decided 2026-11-01).
- Visibility scoping in shared spaces uses buckets: static row filters plus equality bucket columns; subscriptions are derived from tokens at the gateway; one cookie per device. Rejected: named views (evaluating all views on write prevents writes when views are unbounded). Trade-off: integrators must partition visibility by columns into buckets. Subscriptions per device are capped, and exceeding the limit is rejected at the gateway (following PowerSync's intent of at most 1,000 buckets per connection; no limit on total buckets across the space): without a cap, merging a chunk across too many buckets can yield zero items within budget and stall forever (decided 2026-10-25). The cap is byte-based: subscriptions encoded as JSON are capped at 8 KB, and the landed subscription is placed directly into the pull URL query string (Cloudflare URLs are capped at 16 KB), allowing ~170 buckets when parameters are UUIDs. Table names are capped at 64 characters (as in MySQL): the cursor in the URL carries the scanned table, and the largest key, bucket, and landed subscription leave about 2 KB (measured 14,193 bytes with a 4-character table name, which appears once; decided 2026-11-04). Rejected: storing subscriptions by hash on the cloud or passing subscriptions in request headers (an extra table or round-trip solely to preserve 1,000 buckets; decided 2026-10-26). Trade-off: patterns like subscribing to hundreds of groups on a single device require a different bucket partition design. Adding buckets scans only the added buckets; removing buckets triggers a full resync (following ElectricSQL where shape changes force a fresh pull). Rejected: removed-bucket scans plus tail reading "previously in old subscription" entries (adds reader code paths and emits deletions to the device for keys modified after revocation but before landing). Trade-off: whenever buckets are revoked, the device re-downloads all visible data from scratch (decided 2026-10-25).
- Cloud records the last processed mutation ID (`lmid`) per client and never deletes it: when cloning or restoring from an old backup, pending writes from older clients can still push. Trade-off: each write-enabled session start leaves ~100 B.
- HTTP pulls for private spaces use POST with request bodies (following Replicache pull); WebSocket URLs carry only the cookie; catch-up on connect confirms clients that committed after the cookie (following Replicache `lastMutationIDChanges`): commit records of device writes record client IDs, which catch-up reads back over the commit range. Rejected: reusing client IDs across launches (mutation identity must never change); capping listed clients (exceeding the limit still breaks connections): listing client IDs for every write-enabled launch in the URL exceeds 16 KB in ~170 launches, permanently breaking connections. Rejected: storing the latest commit version on a client table with an index (Replicache's approach): adds 1 extra row write per client write, an overhead of ~33%. Trade-off: each commit version adds ~36 bytes; catch-up reads at most ~3× the number of commits in rows (row reads cost ~1/1,000 of row writes); internal cloud tables collapsed to one version, staging wiped on deploy; protocol bumped to version 5, requiring staging devices to update the app (decided 2026-10-29).
- Online checksums compare row content by range on demand; if the database changes during verification, the range is halved; ranges proceed sequentially from where the last check left off, up to 1,000,000 rows per device per day (configurable); mismatches re-download only that range. Rejected: maintaining cumulative checksums on write (cannot detect local corruption); random range ordering (corrupted rows exist only locally; sequential scans cover all rows eventually without tracking start points and wrap-around; decided 2026-10-25). Trade-off: large spaces take many days to complete a full pass.
- Downstream notifications carry small changes, falling back to hints when too large, rather than pure beacons: pure beacons would add a billed request per online device on every write. Shared-space fanout is a resumable background task, sending each round to all shards, which filter locally against each connection's subscription (following PowerSync). Rejected: having shards register their subscribed buckets with the shared space (accepting connections would require prior registration at the shared space, dogpiling a single object during reconnect waves after deploys, and adding serialization for concurrent registration and unregistration). Trade-off: under thousands of shards, narrow buckets, and continuous high-frequency background writes, per-write cost scales with the shard count (decided 2026-10-25).
- Fanout delivers to each shard independently: advances only upon acknowledgment; unacknowledged shards back off and retry independently; at most one round in flight per shard at any time; shards never wait on each other. Rejected: broadcasting a single round to all shards simultaneously (a single stalled shard causes every round to wait out the timeout, delaying background write returns under continuous writes). Shard acknowledgments are tracked in memory within the shared space; a value is persisted only when all shards catch up to head; after an actor restart, delivery replays overlapping rounds from the persisted version (decided 2026-10-26).
- Shared spaces wake once an hour (`refreshInterval`) to retry unacknowledged fanout and push tables a deploy rescanned, so a deploy that changes the scope reaches connected idle devices at the next hourly wake: Cloudflare's default `deferred` code update keeps hibernated WebSockets connected and wakes nothing (measured on Cloudflare: a device connected through a deploy heard of it 57 minutes later). Rejected: a shorter wake interval (one alarm per shared space per interval), traffic from devices that wakes the shard (cost grows with devices), an integrator call after each deploy (an extra deployment step). Trade-off: devices learn of the new scope up to an hour late, sooner on server writes, pulls, or reconnects (decided 2026-11-04).
- Broadcast shards track their known version only in memory, not persisting each round: persisting would incur 1 row write per shard per round (128 shards at 1 round per second costs around \$332/month). A shard that lost its known version (reset or eviction) still chains the next non-empty round onto each connection: the shared space sends only from a version every shard of the current shard set acknowledged, persisted with that set, so every connection already holds what came before it. Only the empty round of a fresh fanout (first start, or a changed shard count) makes a shard that knows nothing query the latest version and push hints to all its connections, and devices pull over HTTP (via cache) (decided 2026-10-26; chaining after eviction decided 2026-11-04 with an agent design review, as delegated by the user, and checked by `model/Fanout.tla`). Rejected: pushing hints after every eviction (shared spaces with sparse writes sent every device to HTTP on nearly every round).
- When devices connect to a broadcast shard, send only an empty catch-up (if the cookie matches the latest version exactly) or a hint, matching the model; do not send patch-bearing catch-ups when the cookie happens to match the start of the round known to the shard (avoiding one pull, but omitted from the model; decided 2026-10-26).
- Device read-only data (payments, trials) resides in cloud-written tables (`readOnly`) within private spaces: local writes touching them throw immediately; pushed writes touching them are held (following the unexecutable-write path, modeled analogously to business rejections on synced tables: devices revert local optimistic predictions); resubmissions touching them also throw. Rejected: column-level read-only (device writes are pushed by row; mixing writable and read-only columns in one row requires holding the whole mutation; separate tables are clearer for integrators). Read-only tables must not reference device-writable tables: cascade deletes would allow devices to delete read-only rows by deleting parent rows (decided 2026-11-01).
- Foreign keys reference only the parent table's primary key; declaring a reference to any other column fails opening the database (on devices through `downloadError`) and throws on instantiating `SynclineSpace` (decided 2026-11-03). Rejected: references to non-key columns (SQLite itself requires the parent key to be a primary key or unique; offline devices cannot keep other columns unique, so equal values give a child several parents and cascade deletes and parent checks act on unrelated rows; enforcing uniqueness would add a conflict class contrary to column-level last-write-wins). Trade-off: integrators referencing another column add a column referencing the parent's primary key.
- Rolling back both the cloud and the app after devices synced a release that added a column leaves those devices `ahead` (they still have the column), reconnecting with backoff and keeping pending writes until the cloud declares the column again or an app release retires it (decided 2026-11-03). Rejected: the cloud declaring and accepting undeclared columns still in its database (would accept device writes to cloud-only columns, and contradicts a cloud rollback making the column leave sync); devices syncing leftover columns only while the cloud declares them (fixes the stall, but adds logic across the device declaration, recorder, and pending writes for an operator-caused case).
- Cloud indexes foreign key columns: incurs 1 extra row write per insert or delete on child tables, in exchange for avoiding child-table table scans during cascade deletes.
- Server writes (`mutate`) insert and update through Drizzle one row at a time (deletes on synced tables run in batches of raw SQL), and an update sets only the columns given besides the primary key, plus `$onUpdateFn` columns (setting the key rewrites every index of a WITHOUT ROWID table, each billed as a row written; an update giving only the key still sets it, touching the row). Measured on Cloudflare: a Drizzle point update costs 120–200 µs of CPU against 15 µs for raw SQL, and 9,999-row inserts, bucket moves, and title updates on a wide table with three bucket rules, a foreign key, and validation each finished under a 15 s CPU limit (inserts took 2 s, title updates 3 s), half the default 30 s. Rejected: Drizzle prepared statements (Drizzle evaluates `$defaultFn` and `$onUpdateFn` when preparing, so every row would get the same value); raw SQL (reimplements Drizzle's defaults and value mapping); a set-based `update` taking a condition (a new API no integrator needs yet). Trade-off: large server writes cost several seconds of CPU, so docs advise batches of a few thousand rows (decided 2026-11-04 with an agent design review and measurements).
- Initial device download and full-table resync are atomically visible (written into shadow tables and swapped in after scanning), preventing the UI from observing partial state. After swapping tables, the database file is shrunk in bounded steps as before (decided 2026-10-25): peak storage adds only a constant (the WAL checkpoint threshold), and the database file shrinks back to 1× size. Rejected: retaining free pages for reuse by subsequent writes (database file permanently uses ~2× storage).
- A scheduled task whose run never finishes (it resets the object by exceeding the CPU time limit, or hangs) runs alone on its next attempt, so tasks due with it are not cut off again; after 3 such runs in a row it waits a day before each further attempt and is reported (decided 2026-11-04). Rejected: retrying it every 15-minute lease forever (resets the object, failing in-flight requests, 4 times an hour until the integrator notices); splitting every step (building an index is one SQLite statement); documenting a raised `limits.cpu_ms` alone (the default still resets every lease).
- Opening a database in the foreground while a background `syncOnce` has it open closes that instance and opens a new one with the foreground options (decided 2026-11-04 with an agent design review, as delegated by the user). Rejected: adopting the background instance for the same owner (the foreground token, schema, local-only tables, retired names, and validation would silently not take effect until the next cold start).
- Every synced table has at most one owning space (`_syncline_declared`); an owner switch wipes the rows the previous owner could read outside current declarations: the private space wipes tables no space declares any more, and a shared space wipes the tables it declared last time. Shared owners are independent of the private owner, so rows a shared space pulled never outlive its declarations: a table it no longer declares, or that turns local-only, is wiped when that happens. A table a space declares for the first time while it already holds rows is wiped like a returning one, since those rows would never upload (checked by `model/Ownership.tla`; decided 2026-11-04 with an agent design review, as delegated by the user). Rejected: wiping every synced table the private space does not declare on a private owner switch (would refetch every shared space each time, contradicting the `owner` contract that shared spaces are preserved).
- Device-side architecture is implemented in Rust, managing the local database, networking, and sync internally: iOS and Android via Expo modules, web compiled to WebAssembly inside a dedicated Worker; JavaScript only issues queries, receives notifications, and validates local writes, leaving the JavaScript thread free during all sync steps. The core engine handles neither networking nor timers (receiving events and returning commands from the outside), keeping the local database inside the core; the exact same core compiles to WebAssembly for deterministic simulation and trace validation. Networking on iOS and Android runs in Rust (`rustls`); web uses the Worker's WebSocket. Trade-off: each ABI adds ~0.7 MB (compressed); bypasses system proxies (inferred, not verified on physical hardware); certificates detailed in the next item. Rejected: delegating to platform APIs (`URLSession`, `OkHttp`): heartbeat, reconnect, and backoff logic would need duplicate implementations in Swift and Kotlin. Rejected: Rust as an SQLite extension with JavaScript managing networking: heartbeats and reconnects remain on the JavaScript thread; dynamically loaded extensions cannot access the session API (required for reverting local writes); static linking into `expo-sqlite` requires binding renamed `exsqlite3_*` symbols (internal API subject to breakage on upgrades); falling back to triggers for undo logging would mean rewriting the revert mechanism. Rejected: TypeScript in background JavaScript runtimes: `react-native-worklets` worker threads lack WebSocket support, and execution remains on Hermes. Trade-off: entire device side rewritten in Rust, Rust toolchain added to CI, larger app bundle (decided 2026-11-01). Probe benchmarks (simulator, debug build, 100,000 rows, 10,000 pending writes during one rebase): maximum JavaScript thread blocking of 17 ms on iOS (vs. 2,488 ms in TypeScript) and 17 ms on Android (vs. 3,235 ms in TypeScript).
- Networking details on iOS and Android (decided 2026-11-02):
  - iOS opens sockets directly from Rust, rather than using `URLSession` or Network framework. Firefox iOS, Element X, Signal, and Bitwarden follow this pattern in their Rust cores. Trade-off: as Apple notes, raw sockets do not automatically wake cellular hardware or route through on-demand VPNs.
  - Sync URLs must be `https://`; `http://` is accepted only with the `openSyncline` option `allowCleartext` (for local development, covering the private space and shared spaces). Rust sockets bypass the platform cleartext policies (iOS App Transport Security, Android `usesCleartextTraffic`), so without this check a mistyped URL sends tokens and rows in cleartext (decided 2026-11-03). Rejected: exempting loopback addresses without the option (a second rule, and the Android emulator's `10.0.2.2` would still need it or `adb reverse`).
  - HTTP pulls include `Accept-Encoding: gzip`. Cloudflare compresses Worker JSON responses (verified on staging); WebSockets are not compressed.
  - Certificates: Apple platforms delegate verification to the operating system (`rustls-platform-verifier`), trusting the system trust store and MDM-installed enterprise root certificates, and checking revocation; Android uses bundled Mozilla root certificates (`webpki-roots`). Rejected: delegating to Android system verification: Cloudflare certificates provide only CRLs, and Android system verification fetches CRLs over cleartext HTTP, requiring integrators to configure network security configs that break Metro bundler connections in debug builds; Signal and Element X copy Android Kotlin components and disable revocation checks for this reason. Android does not trust user-installed certificates by default, so system verification provides no advantage on corporate networks. Trade-off: Android root certificates update only with app releases; on Apple devices with trusted enterprise root certificates, corporate proxies can inspect sync traffic (including tokens), matching other system apps.
- Devices judge a connection alive by messages, assuming a slowest link of 1 KB/s: pings pause while a push batch's bytes take that long, and cloud messages over 24 KB become hints. Rejected: judging by send progress (`bufferedAmount` excludes operating system buffers, so the web would keep the rate assumption beside a second heartbeat; bytes the kernel accepts are not progress when the peer stops reading; a fixed stall threshold restarts large batches on intermittent links, working against never stalling); kernel timeouts on native sockets (`TCP_USER_TIMEOUT`, `TCP_RXT_CONNDROPTIME`: per-platform options for a rare case, cutting slow live connections mid-batch). Trade-off: when the operating system keeps a dead connection open (the peer stopped reading, or every byte was acknowledged before it died), a silent disconnect during a large upload goes unnoticed until the pause ends, up to about 2.3 hours for an 8 MiB write (decided 2026-11-04 with an agent design review and measurements).
- The dedicated web Worker is bundled with Syncline; integrators only wrap Metro configuration with `withSyncline`. Integrator Standard Schema validation runs on the main page: Rust returns rows modified by local writes to the page for validation, keeping integrator validation code out of the Worker and declaring tables and options in a single `openSyncline` call. Rejected: running validation in the Worker (integrators would have to write Worker entry points and supply duplicate table definitions on both sides; decided 2026-11-02).
- New device-side dependencies: `tungstenite` 0.30, `ureq` 3.5, `rustls` 0.23 with `ring`, `webpki-roots` 1.0, `jni` 0.22, `libc` (`poll`), `sqlite-wasm-vfs` 0.3, `wasm-bindgen-futures` 0.4.80, and build tool `cargo-ndk` (approved 2026-11-02); `ureq` gzip support (`flate2`), and `rustls-platform-verifier` 0.7 on Apple platforms (approved 2026-11-02).
- Releases (decided 2026-11-02):
  - This repository is a private development repository; a separate public release repository is referenced by integrators via git tags. No npm packages: git tags already pin versions without introducing an additional release channel.
  - The release repository contains only files needed by integrators: `package.json` (with development scripts and `devDependencies` removed), `expo-module.config.json`, Metro config, `src/` source code excluding tests and test helpers (including `cloudflare/`), iOS and Android native wrappers, `README.md`, and `docs/reference/`. Files other than `package.json` are mirrored exactly from this repository, so `README.md` addresses only integrators, and internal development guidance remains in `AGENTS.md`. Rust source code, tests, models, gates, and `docs/internals/` stay in this repository.
  - Binaries (iOS and Android libraries and web WebAssembly) are built locally from clean working trees at repository tags and attached to GitHub Releases on matching tags in the release repository, with a manifest recording the version, repository commit hash, and SHA-256 for each file (following PowerSync `powersync-sqlite-core`). Integrators download prebuilt binaries by version during builds without installing Rust or building from source; the wrapper checks for `rust/` and builds from source if present, preserving normal local development in this repository. Rejected: committing binaries into the release repository (iOS static libraries for three targets exceed 100 MB per release, causing repo bloat). Rejected: building on GitHub Actions (private repositories bill by minute; local builds suffice for a single integrator). Do not publish to CocoaPods trunk or Maven Central: CocoaPods stops accepting new podspecs on 2026-12-02, and Maven Central requires namespace verification and signing.
  - The release repository contains no development history: the first commit is a full snapshot of the initial release; subsequent commits are synchronized in batches during releases (retaining only changes to release files and preserving commit messages, skipping commits that touch no release files) before tagging. No continuous synchronization, preventing release source code from getting ahead of binaries. Pushed commits are never rewritten: integrator lockfiles reference commit hashes. The initial release occurs after full-repository translation to English.
  - Trade-off: binary-to-source matching relies entirely on building from clean tags and cannot be independently verified by integrators; synced commit messages reference internal changes (Rust, tests) not present in the release repository.
- English-only across the repository (decided 2026-11-02): comments, strings, error messages, tests (including Rust and TLA+ models), all documentation (`README.md`, `docs/`, `AGENTS.md`), and commit messages in this repository. Conventional Commits types are restricted to eight: `feat`, `fix`, `change`, `refactor`, `test`, `docs`, `deps`, `chore`; existing Chinese commit messages are not rewritten. Rationale: the release repository copies source code and documentation verbatim, error messages reach integrators, and commit messages sync to the release repository; a single repository language simplifies rules and gates to one standard. Rejected: changing only public-facing files (leaves mixed Chinese and English in `src/` sources and tests); translation during release (translating per release drifts from source). Trade-off: one-time full-repository translation; reading commit messages is slower than reading native Chinese.
- Coverage (decided 2026-11-05): the full `pnpm check` measures line and branch coverage of TS (istanbul, the only provider Workers tests support) and Rust (the workspace sources, through the TS tests on an instrumented wasm build plus the native unit tests, which always run instrumented) and fails below thresholds; the pre-commit `--changed` run does not judge it, as it runs only some tests. Uncovered code that could break one of the four properties gets a unit or random test; other uncovered code is deleted or its reason recorded, never covered by tests written for the number. Wasm has no LLVM profiler runtime: `minicov` 0.3 supplies it, with the unstable `-Zno-profiler-runtime` enabled by `RUSTC_BOOTSTRAP` on the pinned stable toolchain (dependencies `minicov` and `@vitest/coverage-istanbul` approved 2026-11-05). Rejected: a separate coverage command (thresholds nobody runs stop holding); a pinned nightly toolchain for coverage (a second toolchain, measuring a compiler releases do not use); `cargo-llvm-cov` (the pinned LLVM's `llvm-profdata` and `llvm-cov` suffice). Trade-off: the full check takes ~12–15 s longer, the coverage builds take ~2.4 GB under `rust/target/`, and a toolchain bump may require adjusting the unstable flags; `RUSTC_BOOTSTRAP` also lets dependencies whose build scripts probe for nightly (`thiserror`, `proc-macro2`) enable nightly-only paths in the tested builds, which release builds do not take.
