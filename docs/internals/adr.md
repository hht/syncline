# Syncline 的取舍记录

只记用户做过的取舍：选了什么、放弃了什么、为什么。已经实现的规则以代码、测试与模型（[模型与检查](model.md)）为准，这里不复述。
都可以推翻：发现更好的做法就给对比表交用户定，定了改这里。

- 云端按列覆盖、后到为准，照 Drizzle 的外键连带删、拒收引用已删父行的写，不给每张表写 mutator。代价：两台设备同时「读出再改」同一列时后到的覆盖先到的。
- 时间点恢复不封口：游标不在恢复后历史上的设备整份重拉，待上传照常推；写的身份（客户端, 序号）永不改，序号的空缺由云端跳过（重编序号会让从旧备份恢复的设备把同一条写执行两次）。代价：恢复撤不掉设备上还没推的写。
- 提交记录只记改到的键、拉取读当前值，按字节封顶（至多数据的 0.25 倍、至少 64 MB），超了由后台任务截掉最早的；游标早于下限的设备整份重下（共用空间回 reset）。不选按时间保留（写得多时没有上界）、不选带值的日志（私有空间存储约 5.7 倍）。代价：离线很久的设备整份重下；日志到上限后每条提交多 1 行写。
- 主键与位置各只有一种写法：主键编成文本时各列按列名排；位置都用读取器的那一种编法（校验和的起点是其中的扫描点，导出存的就是读取器的位置）。不让两种写法并存：正式还没上线，内部表压回一版，预发清空、设备删库（2026-10-29 定）。
- 表名、列名只许英文字母、数字、下划线，不以数字开头：名字原样拼进 SQL 的 JSON 路径、当主键对象的键，不另做转义。代价：接入方不能用别的名字（2026-10-29 定）。
- 同步范围变了（表或列进入同步、共用空间的桶规则改了）只在范围表里记它从哪一版起，拉取先给离开的、再扫进入的、最后追增量：照 ElectricSQL 改了 shape 就作废、客户端只重下这个 shape。不选写一侧补记（多写、多存一份，可能超出 10 GB）。代价：每台落后的设备各重下这张表。
- 私有空间在设备上是全量副本，设备要装得下整个空间；不做部分同步。
- 换人登录时上一个人还有没上传的写：不清、打开出错（`PendingWrites`，带上一个人与条数），接入方让他登录同步完再换人，或打开时给 `discardPending` 明确丢掉；后台同步不丢。不选照常清掉（PowerSync 的 `disconnectAndClear` 连待上传一起清，由 App 自己先查 `getUploadQueueStats`）：没上传的写再也传不上去。不选每人一个本机库：上一个人的数据留在设备上。代价：接入方要处理这个错误，不处理时换人后打不开库。
- 用户要整份重下（`resync`）默认留着没上传的写：从头整份拉、落地时换掉同步表，待上传照常重放、推上去（与时间点恢复后的整份重拉同一条路，模型的 `Refetch`）；给 `discardPending` 才连它们一起丢。推送里一条写的改动认不出、身份认得出的，云端扣下这一条、照推序号，不整批拒收，设备不必靠丢掉待上传解开；整批认不出（不是一组、超过上限、认不出写的身份）才以 1007 拒收、设备不再推，这时 `sync()` 立刻失败，`resync({ discardPending: true })` 才解开。不选照旧清空：一次重下就丢掉还没推上去的写（2026-11-01 定）。
- 共用空间的可见范围用桶：静态行过滤加等值分桶列，订阅由入口按令牌算出，一台设备一条游标。不选命名视图：写时要对全部视图求值，视图不设限时写不进。代价：接入方要按列分桶写可见范围。一台设备的订阅有上限，超了入口拒绝（照 PowerSync 一条连接至多 1000 个桶的用意；桶的总数不设限）：不设上限时一块要在很多桶之间归并，预算内可能一项也给不出、永远卡住（2026-10-25 定）。上限按字节：订阅编成 JSON 至多 8 KB，落地时的订阅原样放进拉取的网址（Cloudflare 的网址至多 16 KB），一个参数是 UUID 时约 170 个桶。不选按哈希在云端存订阅、或设备另用请求头带订阅：多一张表或多一种来回，只为保住 1000 个（2026-10-26 定）。代价：一台设备订阅几百个组这类用法要换一种分桶。订阅加了桶只扫新加的桶；去掉桶就整份重下（照 ElectricSQL 的 shape 变了要重新拉）。不选去桶扫描加尾巴多读「改前在旧订阅里」的项：读取器多一条路径，还会把撤权之后、这次落地之前被改的行的主键以删除发给设备。代价：每次被撤掉桶，设备把看得见的数据全部重下一遍（2026-10-25 定）。
- 云端记每个客户端处理到第几条，永不删：克隆、从旧备份恢复时旧客户端的待上传还会推上来。代价：每次有写的启动留约 100 B。
- 私有空间的 HTTP 拉取用 POST、请求放正文（照 Replicache 的 pull），WebSocket 的网址只带游标，连上时的补齐确认游标之后有提交的客户端（照 Replicache 的 lastMutationIDChanges）：设备的写的提交记录上记客户端编号，补齐再读一遍这段提交取出。不选客户端编号跨启动复用（写的身份要永不改）、不选只给列出的客户端封顶（超了照样连不上）：网址列出每次有写的启动的客户端，约 170 次就超 16 KB，之后永远连不上。不选客户端表记最近一条提交的版本加索引（Replicache 的做法）：设备的每条写多 1 行写，约多三分之一。代价：每版提交多约 36 字节，补齐至多多读约 3 倍提交数的行（行读约是行写价格的千分之一）；云端内部表压回一版，部署时预发清空；协议升到第 5 版，预发设备要更新 App（2026-10-29 定）。
- 在线校验和按需分段比行内容，对的途中库变了就把段减半，段按顺序接着上次对，每台设备每天至多 100 万行（可调），对不上只重下那一段。不选随写维护累计和：查不出本机损坏；不让段的顺序随机：坏行只在本机，什么顺序一轮都查遍，随机还要记起点、绕回（2026-10-25 定）。代价：大空间一轮要很多天。
- 下行通知带小改动、装不下发提示，不改纯信标：纯信标每台在线设备每次写多一个计费请求。共用空间的扇出是可续做的后台任务，每一轮发给全部分片、分片按每条连接的订阅在本地筛（照 PowerSync）。不选分片登记自己有哪些桶的订阅者：接受连接要先经共用空间登记，部署后全部重连时压在一个对象上，并发的登记与注销还要另加串行。代价：分片上千、桶很窄、后台持续高频写时，每次写的费用随分片数涨（2026-10-25 定）。
- 扇出给每个分片各自一条：确认了才前进，没确认的各自退避再发，一个分片同一时刻只有一轮在路上，分片之间互不等。不选一轮发全体、同一时刻一轮：一个卡住的分片让每轮都等满超时，持续写时后台写迟迟不返回。各分片确认到哪一版只在共用空间的内存里，全部确认到最新一版才落库一个值，对象重启后从落库的那一版重叠地再发（2026-10-26 定）。
- 分片知道到哪一版只在内存里，不每轮落库：每轮每片一行写（128 片、每秒一轮约 $332/月）。代价：分片空闲后被逐出内存，下一轮接不上，给这片的全部连接推提示，设备走 HTTP 拉（经缓存）；写得稀的共用空间几乎每轮如此（2026-10-26 定）。
- 设备连上广播分片时只发空的补齐（游标正好是最新一版）或提示，与模型一致；不在游标正好是分片知道的那一轮的起点时发带改动的补齐（少拉一次，模型里没有）（2026-10-26 定）。
- 设备只读的数据（付费、试用）放私有空间里只由云端写的表（`readOnly`）：设备本机写改到就抛错，推来的写改到就扣下（与执行不了的写同一条路，模型里与同步表上的业务拒收同类：设备撤回本机的预测），重新提交的改到也抛错。不选按列只读：设备的写按行推，一行里混着两种列时只能整条扣下，接入方另拆表更清楚。只读表不能引用设备能写的表：删父行连带删子行，设备会借删父行删掉它们的行（2026-11-01 定）。
- 云端给外键列建索引：子表每插删一行多 1 行写，换来连带删不扫子表。
- 设备首次下载与整张表重下原子可见（写进影子表、扫完换上），不让界面看到一半。换表后照旧分几步收缩库文件（2026-10-25 定）：峰值多一个常数（预写日志的检查点阈值），库文件缩回 1 倍；不选留着空页给之后的写复用：库文件一直多占约一倍。
- 设备一侧用 Rust 写，自管本机库、网络与同步：iOS、Android 经 Expo 模块，web 编成 wasm 放进专用 Worker，JS 只发查询、收通知、校验本机写，同步的任何一步都不占 JS 线程。核心不做网络与计时（收事件、回指令，两者从外面接），本机库在核心里；同一份核心编成 wasm 接回确定性模拟与轨迹核对。iOS、Android 的网络也在 Rust 里（rustls），web 用 Worker 的 WebSocket；代价：每个 ABI 多约 0.7 MB（压缩后），不走系统代理（推断，没实测）；证书见下一条。不选交给平台（URLSession、OkHttp）：心跳、重连、退避要在 Swift 与 Kotlin 各写一份。不选 Rust 写成 SQLite 扩展、JS 管网络：心跳与重连仍在 JS 线程；动态加载的扩展调不到 session 接口（撤回本机写靠它），静态链接进 expo-sqlite 要绑它改了名的 `exsqlite3_*` 符号（不是公开接口，升级就可能断），改用触发器记撤回日志等于重写撤回机制。不选 TS 放后台 JS 运行时：react-native-worklets 的工作线程没有 WebSocket，计算仍在 Hermes 上。代价：设备一侧整个用 Rust 重写，Rust 工具链进 CI，App 包变大（2026-11-01 定）。探针（模拟器、debug 包，10 万行、1 万条待上传做一次 rebase）：JS 线程最长被占 iOS 17 ms（TS 2,488 ms）、Android 17 ms（TS 3,235 ms）。
- iOS、Android 的网络细节（2026-11-02 定）：
  - iOS 也由 Rust 直接开 socket，不改用 URLSession、Network framework。Firefox iOS、Element X、Signal、Bitwarden 的 Rust 核心都这样。代价是 Apple 说的直接用 socket 不会自动唤醒蜂窝网络、不走按需 VPN。
  - HTTP 拉取带 `Accept-Encoding: gzip`。Cloudflare 会压缩 Worker 回的 JSON（预发上实测）；WebSocket 不压缩。
  - 证书：苹果的系统上交给系统校验（rustls-platform-verifier），认系统证书库与 MDM 装的企业根证书、查吊销；Android 用内置的 Mozilla 根证书（webpki-roots）。不选 Android 也交给系统：Cloudflare 的证书只给 CRL，Android 的系统校验要用明文 HTTP 下 CRL，得往接入方的 App 里塞网络安全配置，调试包会因此连不上 Metro；Signal、Element X 为此拷了它的 Kotlin 组件并关掉吊销检查。Android 默认本来就不信任用户装的证书，换成系统校验对公司网络也帮不上。代价：Android 的根证书随 App 更新；苹果上装了并信任了企业根证书的设备，公司的代理能解开同步的流量（含 token），与系统里别的 App 一样。
- web 上的专用 Worker 由 Syncline 自带，接入方只在 Metro 配置里包一层 `withSyncline`；接入方的 Standard Schema 校验在页面做：Rust 把本机写改到的行交回页面校验，接入方的校验代码不进 Worker，表与选项只在 `openSyncline` 给一处。不选校验放进 Worker：接入方要自己写 Worker 入口、两头给同样的表（2026-11-02 定）。
- 设备一侧新增的依赖：tungstenite 0.30、ureq 3.5、rustls 0.23 加 ring、webpki-roots 1.0、jni 0.22、libc（poll）、sqlite-wasm-vfs 0.3、wasm-bindgen-futures 0.4.80，构建工具 cargo-ndk（2026-11-02 批）；ureq 的 gzip（flate2）、苹果的系统上的 rustls-platform-verifier 0.7（2026-11-02 批）。
- 发布（2026-11-02 定）：
  - 本仓是私有的开发仓库，另建一个公开的发布仓库，接入方按 git tag 引用它。不发 npm 包：git tag 已经能锁版本，不多一个发布渠道。
  - 发布仓库只放接入方用得到的：`package.json`（去掉开发用的 scripts 与 devDependencies）、`expo-module.config.json`、Metro 配置、`src/` 里除测试与测试辅助以外的源码（含 `cloudflare/`）、iOS 与 Android 的原生外壳、README 与 `docs/reference/`。除 `package.json` 外照本仓原样复制，所以 README 只写给接入方，本仓的开发说明放在 AGENTS.md。Rust 源码、测试、模型、门禁、`docs/internals/` 留在本仓。
  - 二进制（iOS、Android 的库与 web 的 wasm）在本机从本仓的 tag 的干净工作区编，附在发布仓库同名 tag 的 Releases 上，清单记版本、本仓的提交号与每个文件的 sha256（照 PowerSync 的 powersync-sqlite-core）。接入方构建时按版本下载，不装 Rust、不现场编；外壳看有没有 `rust/`，有就现场编，所以本仓开发照旧。不选提交进发布仓库：iOS 三个目标的静态库每版一百多 MB，仓库越发越大。不选在 GitHub Actions 上编：私有仓库按分钟计费，只有一个接入方时本机够用。不发到 CocoaPods trunk 与 Maven Central：前者 2026-12-02 起不收新的 podspec，后者要验证命名空间与签名。
  - 发布仓库不带本仓的历史：第一个提交是首次发布时的整份快照，之后本仓的提交在发布时成批同步过去（只留发布的文件里的改动、照搬提交说明，没改到发布的文件的跳过），再打 tag。平时不同步，免得发布仓库的源码走在二进制前面。推上去的不改写：接入方的 lockfile 记着它的提交。首次发布在全仓改成英文之后。
  - 代价：二进制对不对得上源码只能靠「从干净的 tag 编」守着，接入方核对不了；同步过去的提交说明会提到发布仓库里看不到的改动（Rust、测试）。
- 仓库里一律英文（2026-11-02 定）：注释、字符串、报错、测试（含 Rust、TLA+ 模型），全部文档（README、`docs/`、AGENTS.md），以及本仓的提交说明。类型照 Conventional Commits，只有八个：feat、fix、change、refactor、test、docs、deps、chore（依次对应原来的新增、修复、调整、重构、测试、文档、依赖、工具）；已有的中文提交不改写。为什么：发布仓库原样复制源码与文档，报错会传到接入方，提交说明会同步进发布仓库；全仓一种语言，规则与门禁只有一条。不选只改公开出去的文件（`src/` 里源码与测试中英混杂）、不选发布时翻译（每版重翻、对不上源码）。代价：全仓一次性翻译，读提交说明比读中文慢。
